控件选错，页面往往不会报错，只会让人犹豫。

一个设置项用了复选框，底部又放着保存按钮；一个表单字段用了下拉菜单；一个只有两个选项的单选，却藏进了下拉选择。它们看起来都能点，但用户会开始猜：现在生效了吗？保存了吗？我刚才点的是值，还是动作？

选择控件的关键，不是长得像不像，而是先回答三个问题：这次选择什么时候生效、它承载的是值还是动作、一共有多少个选项。

## 先问：这次选择什么时候生效？

开关（Switch）和复选框（Checkbox）最容易被混用，因为外观都像“打勾”。

真正的分界线是生效时机：

- **开关**：拨动的那一刻就生效，通常由页面自动保存，不需要再点“保存”。
- **复选框**：表单里的一个答案，随表单一起提交，通常需要一个明确的保存动作。

所以，设置页里的“接收通知”“使用深色模式”适合开关；注册表单里的“同意服务条款”、批量操作里的“全选”适合复选框。

如果一个开关旁边还放着保存按钮，用户就很难判断它到底有没有生效。两种模型只能选一种：

- 即时生效：拨动后立刻请求保存，成功或失败都有反馈，页面上不再出现保存按钮；
- 提交生效：改用复选框，让用户明确知道要按保存。

另一个常见错误，是用两个单选按钮表示一件事的开与关。“开 / 关”本身就是一个布尔值，应该用一个开关。只有当两侧都有独立名称时，它才是一个选择，比如“浅色 / 深色”“按月 / 按年”，这时才轮到分段控件或单选。

## 值是值，动作是动作

下拉选择（Select）和下拉菜单（Dropdown）长得几乎一样，但承载的内容完全不同。

**下拉选择承载一个值。** 选中后，字段里显示当前值，列表里对应的选项带勾选标记。比如语言、时区、每页显示多少条。

**下拉菜单承载一组动作。** 点击某一项会立即执行，触发器保持原来的名字，结果出现在别处。比如“导出”“复制链接”“删除”，或者主按钮旁边的“定时发送”“存为草稿”。

这也是为什么下拉菜单常出现在页面顶部、工具栏和列表行尾，而不是表单字段里。

一个很典型的 bug，是把动作菜单当成了表单字段：用户点了“中文”，按钮仍然写着“语言”，页面也没有显示当前选择。用户不知道刚才那一下是切换了语言，还是只是打开了菜单。

反过来，把“删除”“导出”放进下拉选择，也会让动作看起来像一个可以保存的值。

如果主操作和一组相关动作放在一起，可以用拆分按钮（Split Button）：左边是主操作，右边是同一类动作的菜单。例如“发送”与“定时发送”“存为草稿”。

还有两个容易混淆的控件：

- **标签页（Tabs）**切换的是内容，不设置任何值；
- **分段控件（Segmented Control）**设置一个值，或切换同一内容的不同视图。

如果切换后 URL、内容区域和页面标题都变了，它更接近标签页；如果只是改变了列表的排序或视图模式，它更接近分段控件。

## 2–5 个选项，还是更多？

同样是单选，选项数量决定了控件形态。

- **2–5 个简短选项**：用分段控件，所有选项一目了然。
- **2–5 个需要单独一行的选项**：用单选按钮，竖直排列，标签放在圆圈右侧或下方。
- **6 个以上，或标签长度会变化**：用下拉选择，避免选项把布局撑开。
- **数百个选项**（国家、时区、成员）：用带搜索的下拉选择，并在没有匹配结果时给出清晰的空状态。

分段控件的优势是“看得见”，代价是占空间。选项一多、文字一长，它就会把一行撑成好几行，或者在窄屏上被迫截断。这时下拉选择不是“更高级”，而是更合适的容器。

反过来，只有两个选项时用下拉选择，通常是在给用户增加一次点击。尤其是“开 / 关”“列表 / 网格”这类二元选择，分段控件或开关更直接。

还要注意标签会不会变化。像“负责人”“日期”“项目”这类值会增长、长度不固定的字段，不适合分段控件；用下拉选择或选择器，布局才不会跟着内容跳动。

## 单选还是多选？

单选按钮（Radio）和复选框（Checkbox）的区别，不是“圆圈还是方框”，而是“能选几个”。

- **单选**：恰好一个，所有选项可见，适合问卷这类需要列出全部选项的单选题。
- **复选框**：任意数量，包括一个都不选。

单选一旦选中就无法取消，所以在“不确定”“不想回答”“无”本身是合理答案时，要把它作为一个选项列出来，而不是让用户被困住。

在下拉选择里，这条规则同样成立：

- 单选时，选中项后面用勾选标记（checkmark），不要画一个单选圆圈；
- 多选时，每一项前面用复选框，选中的值以标签（chip）的形式显示在字段里。

单选组用 `fieldset` 和 `legend` 关联问题与选项，键盘用方向键切换；复选框和开关用空格键切换，开关还要向屏幕阅读器暴露 `role="switch"` 与 `aria-checked`。

## 几个常见反模式

- **用两个单选表示开 / 关**：一件事的布尔状态用一个开关，除非两侧各有独立名称。
- **开关放在需要保存的表单里**：用户不知道拨动是否已经生效。要么即时保存，要么换成复选框。
- **把动作菜单当表单字段**：选完后触发器不显示当前值，用户无法确认选择结果。
- **两个选项也用下拉选择**：多一次点击，还把选项藏了起来。
- **八个长选项也用分段控件**：窄屏上必然换行、截断或横向滚动。
- **自定义下拉选择破坏键盘和移动端**：原生 `<select>` 在移动端往往更可靠；自定义列表要补齐方向键、输入跳转、Esc、焦点回归和屏幕阅读器语义。
- **切换控件类型时丢掉已保存的值**：从单选改成下拉选择，原选项必须能正确映射；不能默默回到默认值。
- **用占位符代替标签**：用户输入后标签消失，就不知道这个字段是什么。
- **禁用选项不解释原因**：至少说明为什么不可选，以及怎样才能解锁。

## 一张决策表

| 场景 | 首选控件 | 生效时机 | 备注 |
| --- | --- | --- | --- |
| 设置页里的通知、主题、自动保存 | 开关 | 即时 | 不再提供保存按钮 |
| 表单里的多项选择 | 复选框 | 提交时 | 与保存按钮配合 |
| 一件事的开 / 关 | 开关 | 即时 | 不要用两个单选 |
| 两个有名字的互斥选项 | 分段控件或单选 | 视场景 | 如浅色 / 深色 |
| 2–5 个简短的单选项 | 分段控件 | 即时或提交 | 全部可见 |
| 2–5 个较长的单选项 | 单选按钮 | 提交时 | 每项一行 |
| 6 个以上、标签会变化 | 下拉选择 | 提交时 | 布局稳定 |
| 数百个选项 | 带搜索的下拉选择 | 提交时 | 处理无结果状态 |
| 工具栏、行尾的一组动作 | 下拉菜单 | 点击即执行 | 触发器保持动作名 |
| 主操作 + 相关动作 | 拆分按钮 | 点击即执行 | 主次分明 |
| 切换内容视图 | 标签页 | 即时 | 不设置值 |

## 检查清单

- 每个控件都能用一句话说清楚：它设置什么，或者执行什么。
- 生效时机与页面上的保存按钮一致，用户不需要猜。
- 选项数量、标签长度和屏幕宽度匹配当前控件。
- 单选、多选的语义正确，不会出现“只能选一个的复选框”。
- 从旧控件迁移到新控件时，用户已经保存的值不会丢失。
- 键盘可以完成全部操作，焦点顺序合理，Esc 能关闭浮层并把焦点还给触发器。
- 开关、单选组、复选框都有可访问名称，状态变化能被屏幕阅读器读出。
- 移动端使用原生控件或等价的可靠交互，触摸目标足够大。
- 选项很多时有搜索、加载、空结果和错误状态。
- 文案描述的是结果，不是控件本身，例如“接收邮件通知”，而不是“开关”。

  下拉选择，保证布局不跳动。
- 数百个选项（时区、国家、成员）：带搜索的下拉选择；没有匹配结果时给出明确提示。

d. 单选还是复选框：看能选几个。
- 单选：恰好一个，所有选项可见，适合问卷这类单选题。选中后通常无法

- 复选框：任意数量，包括一个都不选。
- 在下拉选择里：单选用勾选标记，不要画单选圆圈；多选在每一项前放
  复选框，选中的值以标签（chip）显示在字段里。

## 质感来自可解释的细节

控件选择不是审美问题，而是语义问题。

开关说明“这件事现在生效”，复选框说明“这是表单里的一个答案”，下拉选择说明“这里有一个当前值”，下拉菜单说明“这里是一组可以执行的动作”。用户不需要学习你的组件库，也能从形态和位置读出这些含义。

当每个控件的生效时机、承载内容和选项数量都一致时，页面会变得安静：用户不再反复确认，也不再担心自己刚才点错了什么。
