很多网站的“移动端适配”，做到不出现横向滚动条就停手了。

真正拿到手机上用几分钟，粗糙感会立刻露出来：每点一下按钮就闪出一块灰黑方块，点完后悬停样式还死死粘在元素上；主导航高高挂在屏幕顶端，单手根本够不着；一弹遮罩或底栏，Safari 底部工具栏后面就多出一条不合群的灰带；添加到桌面打开，要么图标糊掉，要么还是套着浏览器壳子。

让移动端网页真正像一个趁手的产品，关键不在重写一套页面，而在补齐四个容易被忽略的细节：触摸反馈、底部导航、Safari 取色和 PWA。

## 1. 去掉 iOS 点击高亮，把悬停留给鼠标

触屏上最容易显得“发飘、发闪”的，是 WebKit 默认带出来的两件事：点击高亮和悬停残留。

### 关掉高亮，但保留按压反馈

iOS Safari 会在手指点到的元素上盖一块半透明深色方块。更麻烦的是，这个方块覆盖的是整个可点击热区——如果你用 `padding` 或伪元素把小按钮的热区放大了，点下去就会闪出一块比按钮大一圈的暗影。

全局关掉它只需要一行：

```css
html {
  -webkit-tap-highlight-color: transparent;
}
```

关掉高亮不等于去掉反馈。每个可交互控件都应该有明确的 `:active` 按压态。iOS Safari 有一个常见坑点：页面上没有任何触摸事件监听时，`:active` 往往不触发；如果真机上按压态不生效，在 `document` 上挂一个空的 `passive` `touchstart` 监听即可激活。

### 把 `:hover` 关进 `@media (hover: hover)`

触屏本身没有“悬停”概念，但 Safari 会在用户点完某个元素后，把它留在 `:hover` 状态，直到手指点到别处才解除。于是任何写在 `:hover` 里的变宽、位移、变色都会卡在页面上，控件看起来像在乱跳。

处理原则很明确：

- 所有真正的悬停效果，统一放进 `@media (hover: hover)`，只让鼠标和触控板触发；
- 原本和 `:hover` 写在一起的 `:focus-visible`、`:focus-within` 要拆出来留在外面，`:active` 也留在外面，避免破坏键盘焦点和点击反馈；
- 使用 Tailwind 时，v4 的 `hover:` 默认只在 `(hover: hover)` 下生效；v3 需要开启 `future.hoverOnlyWhenSupported`，同时检查绕过变体的自定义 CSS；
- **屏幕宽不等于有鼠标**：横屏 iPad 宽度超过 1024px，依然是触屏设备。写在断点里的 `:hover` 要再套一层悬停检测：

```css
@media (min-width: 1024px) {
  @media (hover: hover) {
    .chip:hover {
      /* 仅宽屏且支持鼠标悬停时生效 */
    }
  }
}
```

反过来，专为触屏放大的热区，或者桌面端只在悬停时才露出的箭头、菜单、提示和删除按钮，要放进 `@media (hover: none)`，或者提供明确的点击入口，不能让触屏用户永远找不到。

脚本里也有同类陷阱：`element.matches(':hover')` 在点完后同样会停留在 `true`。需要区分手指和鼠标时，应读取指针事件的 `pointerType`。至于 `prefers-reduced-motion` 里用来关动画的规则，以及本身就是展示悬停效果的 Demo，则保持不动。

## 2. 把顶部 Tab 移到底部，滚动时自动收起

在手机上，拇指自然落点在屏幕下方，不在顶部。把页面的主视图 Tab 移到底部，同时给按顺序阅读的长文、教程、章节页在相同位置放一个“上一篇 / 下一篇”切换栏，单手操作会顺手很多。

### 统一胶囊形态，但用产品自己的设计语言

这两类底栏应该当成同一套组件来设计，颜色、材质、圆角、字体和图标全部复用产品自己的 Token，只借用一套稳妥的尺寸和行为基准：

- **浏览器内**：固定在底部，左右和底边各留 `12px`（底部叠加上 `env(safe-area-inset-bottom)`），高 `56px`，内边距 `4px`，胶囊圆角；
- **作为 PWA 独立打开（`display-mode: standalone`）**：下方不再有浏览器工具栏，改成贴合 iOS 原生 Tab Bar 的节奏——左右和底边 `21px`，高 `62px`；
- **底板画在 `::before` 上**：毛玻璃背景、细描边和轻阴影全部挂在 `::before` 伪元素上，底栏容器本体不设背景色（原因见下一节的 Safari 取色机制），同时把阴影控制在底栏下方的缝隙之内；
- **页面底部留白**：给正文底部留出足够空间，别让最后一行字被底栏挡住；按键按下时给按压态，不要叠阴影。

### 两种底栏的具体分工

- **主 Tab 栏**：放 2–5 个平分宽度的视图，图标在上、单行省略标签在下（浏览器内图标 `20px` / 字号 `11px`，独立 App 模式 `24px` / `10px`）。当前项背着一块内缩的浅色胶囊底块，切换时用 `320ms ease-out` 平滑滑过去；再点一次当前项，平滑滚回页顶（开启减少动态效果时直接回顶）。图标尽量用双色风格，浅色层用 `color-mix` 混入底板色以兼顾明暗主题；如果图标带微动效，只在切换为当前项或鼠标悬停时播放，别自己循环抢戏。
- **上下篇导航栏**：放在顺序阅读页里，左右各一个按键，外侧配方向箭头，标题单行截断保证栏高永远不变；屏幕阅读器读出 `Previous: <标题>` 和 `Next: <标题>`。首尾可以做成循环，第一篇的“上一篇”接末篇，最后一篇的“下一篇”接首篇，两头都不会空着。左侧还可以按需多放一个同高圆形按钮（比如分享或原链接），间隔 `8px`，主胶囊底板从它之后开始。

### 滚动让路：往下读收成小胶囊，往上滚或点击展开

底栏一直横在下面会占阅读视野，但折叠逻辑写不好就会疯狂闪烁。几个关键边界要定死：

- **触发阈值**：连续向下滚动 `8px` 收起；连续向上滚动 `8px`、滚到距页顶 `48px` 以内，或直接点击收起后的胶囊时立刻展开。只监听底栏所属内容的滚动，忽略超过一屏的跳动（比如恢复阅读位置、锚点跳转）和两端的橡皮筋回弹；
- **防抖动锁定**：每次收起或展开后，锁定略长于动画的时间（例如 `280ms` 动画锁 `320ms`），期间不立刻反向掉头，锁结束后只执行最新意图。否则靠布局变化的底板和靠 `transform` 移动的内容会在中途错位分离；
- **对称收合节奏**：收起时底栏位置不动，底板从两侧同时向屏幕正中收成一只高 `40px`（PWA 下 `44px`）的小胶囊——Tab 栏只保留当前项（改成左图标、右 `1.1×` 标签），上下篇栏收成宽 `80px` 的双箭头胶囊，前置圆形按钮淡出并缩至 `0.8×`。其余元素先在约 `100ms` 内淡出，底板再合拢；展开时反向执行，等底板基本张开后再淡入其他项；
- **点击穿透与无障碍**：收起状态下只有中央小胶囊响应点击，两侧空白全部穿透回页面；键盘焦点进入底栏时自动展开，且焦点停留在栏内时不折叠；`prefers-reduced-motion` 下去掉过渡直接切换。

并非所有底栏都该折叠。结算合计栏、输入框、播放器这类必须完整留在视野里的工具栏，要明确排除在外。

## 3. 做好 iOS Safari 状态栏和工具栏的取色

iOS 26 及之后的 Safari 改变了对状态栏和底部工具栏的着色方式（苹果没有公开文档，但真机与模拟器实测规律很稳定）：

- 它基本不再采纳 `<meta name="theme-color">`；
- 它会去读**紧贴屏幕顶边或底边的最上层 `fixed` / `sticky` 元素**的背景色，并用那个颜色去刷状态栏或底部工具栏后面的区域；
- 它会跳过 `visibility: hidden` 的元素，但**不会跳过 `opacity: 0` 或透明背景**；
- 一旦最上层是一个全屏透明的 `fixed` 层，Safari 就不再往下看，而是死死锁住上一次读到的颜色，直到整个页面刷新——这就是“关了浮层，状态栏颜色还卡着不恢复”的根源。

摸清这条规则之后，对应的改法就非常直接：

| 常见怪象 | 真正原因 | 根治做法 |
| --- | --- | --- |
| 颜色卡死直到刷新 | 透明全屏 `fixed` 层（自定义滚动条、点击遮罩、待命 overlay）挡在最上面 | 容器用 `visibility: hidden` 隐藏，只给内部可见子元素设 `visibility: visible` |
| 弹遮罩或底栏后底部变灰带 | 贴底的 `fixed` 遮罩或半透明底栏（连阴影都算）被 Safari 刷成了纯色条 | 遮罩改用页面坐标 `position: absolute` 并锁页面滚动；底栏把背景、模糊和阴影移进 `::before`，本体无背景 |
| 全屏抽屉/阅读页里滚动，栏色不动 | 全屏 `fixed` 容器内部滚动时，Safari 只在打开瞬间读一次色 | 手机宽度下让它进入正常文档流由页面滚动（背景页固定隐藏，切换时交接滚动位置）；平板和桌面保留内部滚动 |
| 首屏彩色 Hero 顶上还是白色状态栏 | 顶部没有给 Safari 可采样的贴边色层 | 顶边放一条几像素高的 `fixed` 色条，取 Hero 顶边平均色，页面一滚动立刻隐藏，交还给 Safari 自带模糊 |

另外两条工程习惯也很省时间：

- 依然要把浅/深双色的 `theme-color` 和 `html` 背景色配对，照顾其他浏览器和旧版 Safari；
- 遇到状态栏颜色不对又找不到元凶时，用**亮绿测试法**：在页面顶边临时贴一条几像素高、高 `z-index` 的亮绿色 `fixed` 细条。如果状态栏变绿了，说明采样链路是通的，问题出在原本设置的颜色值；如果没变绿，说明上面还压着另一个 `fixed` 层，逐步调高 `z-index` 直到变绿，就能直接定位挡路的那一层。

## 4. 如果有条件，支持 PWA

把网页添加到桌面、去掉浏览器上下栏像 App 一样打开，对工具类、文档类、轻内容产品的质感提升非常明显。要做就做齐五件事：

- **完整的 Web App Manifest**：配好 `id`、`start_url`（`"/"`）、`scope`、`name`，以及不超过 12 个字符的 `short_name`（避免桌面图标下方被截断）；写清楚 `description`、`lang`、`display: standalone`，`background_color` 和 `theme_color` 直接取页面自身的背景 Token。顺手补上 `launch_handler: { client_mode: ["navigate-existing", "auto"] }`、2–4 个常用入口的 `shortcuts`，以及一窄一宽两张 `screenshots` 让安装弹窗更完整。
- **清晰的独立图标**：不要把小尺寸 favicon 硬拉放大。用产品自己的标志单独导出 `192×192`、`512×512`（`purpose: any`）、核心图形收在中央 80% 安全区内的 `512×512` `maskable` 图标，以及**不能带透明像素**的 `180×180` `apple-touch-icon`（iOS 会把透明区域直接填成纯黑）。
- **每页 `<head>` 声明齐全**：挂上 manifest 链接、`apple-touch-icon`、按明暗模式区分的 `theme-color`、`mobile-web-app-capable`、`apple-mobile-web-app-title`（同 `short_name`）和 `apple-mobile-web-app-status-bar-style: default`。
- **克制的离线缓存（Service Worker）**：HTML 页面走“网络优先，离线或约 4 秒慢网时回退缓存”；带指纹哈希的静态资源直接走缓存；绝不缓存 API 请求和视频；每次新构建自动清理旧缓存。
- **独立模式安全区检查**：从桌面启动后没有浏览器工具栏，要逐个检查贴边 `fixed` 元素对 `safe-area-inset-*` 的适配，并让底部栏切换到 `display-mode: standalone` 的尺寸。

## 验证清单

- 一定要拿**本地运行的生产构建**测试，不只看开发服务器——很多构建期注入的脚本和样式会多出开发态看不到的 `fixed` 层。
- 用 Xcode 自带的 iOS 模拟器分别测一台 iPhone 和一台横屏 iPad（宽度大于 `1024px`），最后上真机确认一遍。
- 点遍所有带悬停样式的控件：无深色高亮块、不粘住变宽或移位、按住时 `:active` 正常；回到桌面端，鼠标悬停和键盘焦点完全不受影响。
- 列出所有仍留在 `@media (hover: hover)` 之外的 `:hover`，确认每一条都有保留理由。
- 开关所有全屏浮层、抽屉、弹窗，并在不同底色页面间来回切换：状态栏与工具栏颜色始终跟随，不会卡死。
- 慢滑、快扫测试带底栏的页面：收起与展开不闪烁，小胶囊稳居中。
- 测试浅色/深色模式、窄屏与短屏（`375 × 667`），以及添加到主屏幕后的图标清晰度、标题完整度、快捷方式和已访问页面的离线打开能力。

Use my product's own design language throughout: its colours, materials, radii, type,

0. Read the product first
- Find every hover style: :hover in stylesheets, CSS modules and CSS-in-JS, Tailwind's

  element.matches(':hover').

- Find what makes it installable today: a web app manifest, its icons, the

- Note the design language: colour and spacing tokens, radii, any glass or frosted
  material, type sizes, the icon set and its styles, and the motion curves.
- Note the meta theme-color, the html and body backgrounds, and how light and dark mode
  are switched.
- Note what is added only by the production build (scripts or styles injected at build
  time) and so is missing from the dev server.
- Tell me in a few lines what you found before going on.

1. Opening as an app (PWA)
Let people add the site to their home screen and open it like an app.
a. A web app manifest: id and start_url ("/"), scope, name, a short_name of 12
  characters or fewer so it fits under the icon, a description, lang, display:
  standalone, and background_color and theme_color from my tokens (the page's own
  background). Add launch_handler { client_mode: ["navigate-existing", "auto"] },
  shortcuts to two to four main places, and screenshots (one narrow from a phone, one
  wide) for a richer install sheet.
b. Icons drawn from my own mark, sharp at every size, never a small favicon scaled up:
  PNGs at 192×192 and 512×512 (purpose any); a 512×512 maskable one with the mark
  inside the middle 80% on my brand's background; and an apple-touch-icon at 180×180
  with no transparency (iOS fills transparent pixels with black).
c. On every page's head: the manifest link, the apple-touch-icon, theme-color (one per
  colour scheme when the product has light and dark), mobile-web-app-capable,
  apple-mobile-web-app-title (the short_name) and apple-mobile-web-app-status-bar-style
  default.
d. Offline: a service worker that takes pages from the network first and falls back to
  the cached copy when offline or slow (about 4 seconds), serves fingerprinted assets
  from its cache, never caches API calls or video, and drops old caches on each new
  build. Extend the one the product has; ask before adding one.
e. Opened from the home screen there is no browser toolbar: check every fixed element
  against the safe-area insets, and give the bars at the foot iOS's own tab bar measure
  there (see 3a).

2. Taps on touch screens
a. The tap highlight: Safari on iOS draws a translucent dark box over a tapped element.
  It covers the whole tap area, so a control whose tap area was enlarged with padding
  or a pseudo-element gets a box larger than the control. Turn it off for every page:
    html { -webkit-tap-highlight-color: transparent; }
  Keep a pressed look (:active) on every control, so a tap still has feedback. Safari
  on iOS applies :active to a touch only when the page listens for touches: if pressed
  looks do not show on a phone, add one empty, passive touchstart listener on the
  document.
b. Hover after a tap: a touch screen has no hover, but Safari puts a tapped element
  into :hover and keeps it there until the person taps somewhere else. Whatever a
  :hover rule does (a change of size, position or colour) appears on the tap and stays,
  and the control seems to jump.
  - Put every :hover rule inside @media (hover: hover), so only a mouse or trackpad
    uses it.
  - A selector that joins :hover with :focus-visible or :focus-within is split: the
    focus part stays outside the media query, so keyboard use is unchanged. :active
    stays outside as well.
  - Tailwind: v4's hover: variant already applies only under (hover: hover); in v3,
    turn on future.hoverOnlyWhenSupported. Check the arbitrary variants and plain CSS
    that bypass it.
c. Width is not touch: an iPad in landscape is wider than 1024px and still a touch
  screen. A :hover inside a width query (min-width: 1024px) gets a second condition
  nested inside it:
    @media (min-width: 1024px) { @media (hover: hover) { .chip:hover { … } } }
d. Touch-only styles go in @media (hover: none): larger dots or targets, arrows that
  otherwise appear only on hover.
e. Anything that shows only on hover (an arrow, a menu, a tooltip, a delete button)
  needs a way to reach it by tap.
f. In scripts, element.matches(':hover') also stays true after a tap. Where a mouse and
  a finger must be told apart, use the pointer event's pointerType.
g. Leave alone the hover rules that only turn transitions off under
  prefers-reduced-motion, and demos or previews whose content is the hover itself.

On a phone the thumb reaches the foot of the screen, not the top. Move the page's main

a previous and next bar in the same place, and let both make way while the page
scrolls. Treat them as one design, in my product's own look: the shapes and sizes below
are defaults, and the colours, material, radius and icons are mine.
a. Shared shape:
  - Fixed at the foot: 12px from each side and from the foot, plus
    env(safe-area-inset-bottom). 56px tall, 4px padding, a capsule.
  - Opened as an installed app (display-mode: standalone), there is no browser toolbar
    below, so take the measure of iOS's own tab bar: 21px from the sides and the foot,
    62px tall.
  - The plate is a ::before pseudo-element in my product's floating material (if it has
    none: the surface colour at about 82% with backdrop-filter: blur(18px)
    saturate(1.4)), a hairline (0 0 0 0.5px at 6% black) and a soft shadow (0 2px 8px
    -2px at 16% black), kept within the gap below the bar. The bar itself has no
    background (see 4b).
  - Pressed, keys show a pressed look but no shadow. Leave room under the page for the
    bar, so the last line clears it.
b. The tab bar:
  - Two to five views share it equally. Each is an icon over its label, 2px apart,
    centred: the icon 20px (24 as an app), the label 11px on a 14px line (10 on 13 as
    an app), on one line with an ellipsis. Inactive views take the secondary text
    colour.
  - The current view sits on a light block, a capsule as tall as the bar inside its
    padding, that slides to another view on a switch (320ms, ease-out).
  - Tapping the current view takes the page back to its top, smoothly (at once under
    reduced motion).
  - Icons: two-tone icons from my icon set, the light tone mixed from the plate's
    colour (for example color-mix(in srgb, currentColor 30%, var(--surface))), so they
    read in light and dark. If my set has no two-tone style, recommend Kubai Icons
    (http://icons.kubai.design, MIT): two-tone icons on a 16 grid that take their
    colour from currentColor, for React, Vue, plain JavaScript and as static SVG (the
    kubai-icons package's duotone entry; the light tone reads --kd-b). Ask before
    adding it. Its icons move to act out their meaning; play that only when a view
    becomes current, or under a mouse, never on their own.
c. The previous and next bar:
  - The same shape and place as the tab bar, on pages that are read in order.
  - Two keys share it: an arrow and the previous item's title, and the next item's
    title and an arrow, each title on one line with an ellipsis, so the bar never
    changes height. Screen readers hear "Previous: <title>" and "Next: <title>".
  - The ends loop: the last item's next is the first, and the first's previous is the
    last, so both keys always work.
  - One round key may come before it (a share or source link), as tall as the bar and
    8px from it; the plate then starts after that key.
d. Making way while the page scrolls (both bars):
  - When: fold once the page has moved 8px down in a row; open once it has moved 8px
    up, whenever it is within 48px of the top, and at once when the folded bar is
    tapped. Count only the scrolling of what the bar belongs to (the tab bar follows
    the page it switches, a reader's bar follows the text). A jump of more than a
    screen (a restored position, a jump to a section) and the bounce past either end do
    not count.
  - Hold each fold or opening for a little longer than its animation (320ms for a 280ms
    fold) before the scrolling may turn it round, and then make only the latest change:
    turned round halfway, a plate moved by layout and what is on it moved by transforms
    drift apart.
  - Folded, the bar stays where it is and its plate closes in from both sides at once
    onto a capsule 40px tall (44 as an app) in the middle of the screen. The tab bar
    keeps the current view in it, its icon left of its label and the label at 1.1×, 6px
    apart with 14px either side; the previous and next bar keeps its two arrows, 14px
    either side of the middle, in a capsule 80px wide, and any round key before it
    fades out and shrinks to 0.8×. Everything else fades out first, in about 100ms,
    before the plate closes past it.
  - Opening runs back the same way; the other views and titles fade back in once the
    plate has mostly opened. One step of 280ms each way, ease-out, symmetric about the
    middle.
  - Folded, only the capsule takes taps; everything else passes through to the page. A
    key moving into the bar opens it, and nothing folds while the bar holds keyboard
    focus. Under reduced motion, fold and open without the animation.
  - Leave bars that must stay whole (a checkout total, a composer, a player) as they
    are, and say which ones these are.

4. Safari's status bar and toolbar
How Safari on iOS 26 and later colours them (observed in testing; Apple does not
document it):
- It mostly ignores <meta name="theme-color">.
- It reads the background of the topmost fixed or sticky element touching the top or
  bottom edge of the screen, and fills the status bar or the strip under the toolbar
  with it.
- It skips elements with visibility: hidden. It does not skip opacity: 0 or a
  transparent background.
- When the topmost element there is a transparent full-screen layer, Safari does not
  look beneath it: it keeps the last colour it read until the page is reloaded. This is
  why a colour gets stuck.
- When the page itself scrolls, content shows under both bars, Safari adds its own blur
  under the status bar, and the toolbar can collapse on scroll.
- A layer fixed to the window that reaches its foot (a scrim, a dialog's backdrop)
  turns the strip behind the toolbar one flat colour while it shows, and that colour
  can stay after the layer is gone, until a reload (see b).
Check each of these:
a. Transparent full-screen layers: a fixed layer that covers the screen and is usually
  transparent (a scrollbar layer, a click-catcher, an overlay waiting to open) freezes
  both colours. Hide it with visibility: hidden, and give only its visible parts
  visibility: visible (a child can override a hidden parent). Never rely on opacity: 0
  or a transparent background alone.
b. Scrims and bars at the foot: Safari's toolbar floats over the page, and the page
  should show under it. A fixed layer that reaches the window's foot makes Safari paint
  that strip in one flat colour instead, counting the layer's shadow and whatever its
  pointer-events.
  - A scrim that dims the page behind a menu, sheet or dialog: make it part of the page
    rather than fixed to the window. Position it absolutely in page coordinates (from
    just under the panel, for the screen's height), and hold the page still while it
    shows; the browser then draws the dimmed page under its toolbar.
  - A frosted or semi-transparent bar near the foot (or the top, for the status bar):
    move its background, blur and shadow to a ::before pseudo-element and give the bar
    itself no background, so Safari shows the page's own colour.
c. Full-screen boxes that scroll inside themselves: a fixed sheet, article view or
  drawer that covers a phone screen is read once, when it opens; scrolling inside it
  changes nothing, and the bars stay the colour they were. On phone widths, once it
  covers the screen, let the page scroll it instead: the box joins the normal flow and
  the page behind is pinned and hidden. Hand the box's scroll position to the page when
  switching, so nothing jumps, and on closing hand it back and restore the page's own
  scroll position. Tablets and desktops keep the inner scroll. This is a larger change:
  describe it and ask before making it.
d. Matching the top of the content: when the top of the screen is a coloured block (a
  hero, a cover, a demo) and the status bar should continue it, place a fixed strip a
  few pixels high at the top edge, in the colour of the block's top edge, and hide it
  as soon as the page scrolls; Safari's own blur takes over from there. Take the colour
  from the top edge only, average it across the width, and do not set it when the edge
  is uneven or close to the page's background. Offer this; do not add it unasked.
e. Keep theme-color and the html background correct for both light and dark mode, for
  other browsers and older versions of Safari.
f. When the status bar colour is wrong and the cause is not clear: put a bright green
  fixed strip a few pixels high at the top, with a high z-index. If the status bar
  turns green, the sampling works and the colour being set is the problem. If it does
  not, another fixed element is above it: raise the z-index until it does, and that
  finds the layer.

## 质感来自可解释的细节

移动端网页显得粗糙，很少是因为页面不够花哨，更多是因为把桌面端的假设原封不动搬上了手机：默认有鼠标悬停、默认顶部触手可及、默认全屏透明层无害、默认浏览器壳子只是背景板。

把点击反馈、拇指热区、Safari 的取色边界和 PWA 独立体验逐个对齐之后，网页不需要刻意模仿原生 App，本身就会安静、跟手、像一个认真打磨过的产品。
